# V10-min8 r2 — DB参照固定・単位・状態遷移

## 今回の実装
- 比較開始時の `session()` がproviderを開く。Technique、装備Resolver結果、効果Resolver結果を同一sessionでキー別コピーキャッシュ。通常/最大、A/Bで同じ内容を参照し、呼出元に渡すデータはコピー。キャッシュはセッションが有効な間だけ保持。
- 読取のキーはTechnique ID+版、装備は入力+装備DB版+ゲーム版、効果は解決Build+条件+channel+効果版。キーの正規化はプロパティ順に依存しない。
- `effect.unit` は add/cap では**操作先の量の単位**と一致すること。multiplyのamountは無次元で `unit='dimensionless'`。これは数値意味の契約で、実ゲームの単位変換と丸めは未実装。
- consumeイベントはDB定義の`resource` と `amount` を検証し、Handlerが返すnextStateは共通実行器の期待値と完全一致しなければ拒否。transitionイベントはDB定義の `updates` を適用した状態と完全一致させる。Hitそのものの発生判定はHandlerに残す。
- 未定義のDB状態操作は未完了として集約結果を保留する（不正な0は禁止）。

## 制限・今後の構造確認
- Provider自体の元オブジェクトが変動し得ても**同一キーで一度読み取った結果**はセッション中固定。ただし、比較開始前に全必要データを先読みする方式ではない。A側が先に読みB側で初めて要求されるキーはその時点で初読取となる。セッション全体の完全なDBスナップショットを保証するにはProvider側で固定した参照を提供する必要がある。
- `state` がトップレベル単純オブジェクトであることを仮定するconsume契約。実武器状態がネストされる場合はリソースパスと原子遷移を契約化する必要がある。
- L3の条件に未知値がある場合は未解決。state/target/event比較の意味は今後の実スキーマAdapterで要照合。
- 共通計算における表示属性→内部属性の変換、game-specific丸め、全スキル効果は未対応。
- 既存製品への接続、実DB読み込み、ブラウザE2Eは未実施。
- `snapshot-unit-transition.test.cjs` に4件の契約テストを追加したが、GitHub HEADでの実行結果は**未確認**。テスト合格とは主張しない。
